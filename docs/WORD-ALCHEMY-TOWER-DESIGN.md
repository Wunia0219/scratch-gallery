# 英文字根煉金爬塔：實作設計筆記

> 狀態：Scratch 原型持續迭代中。題庫與本機遊戲紀錄已實作；網站排行榜 API 仍屬後續規劃。

## 遊戲定位

- 類型：英文詞綴煉金 × 回合制 RPG 對戰 × 無盡爬塔。
- 學習目標：辨認常見前綴／後綴、字根與合成單字的意思。
- 核心挑戰：答對能煉成法術、打敗更強的敵人，持續衝擊自己的最高分與公開排行榜。
- 目標對象：國小學生。規則先易懂、每一局可在短時間內完成，再透過更高樓層增加深度。
- 排行榜定位：友善公開排行，不是正式競賽，也不使用帳號或密碼。

## 已確認的原則

1. 遊戲開始時由玩家填寫「排名名稱」；Scratch 原型為了用輕量點陣字形顯示，限制為 1–8 個英文字母或數字。
2. 名稱是排行榜顯示標籤，不是帳號；同一玩家可以每次使用不同名稱。
3. 同名不禁止，也不驗證是否為同一人；同名只保留最佳成績。
4. 排名先以樓層由高到低排序；樓層相同時，再以分數由高到低排序；兩者皆相同時保留較早紀錄。
5. 遊戲採 **像素風格**。後續請協助產圖時，所有遊戲視覺素材都以本文件的像素規格為準。
6. 現有的遊玩次數功能不改作排行榜使用；高分榜會使用獨立的 Netlify Function 與 Blob 儲存區。

## 單字題庫

題庫唯一來源是專案根目錄的 `girrafe.json`，目前共有 100 個不重複的單字配方：67 個前綴題、33 個後綴題。每題另有 `translation` 欄位，答題結果會同時顯示自然的繁體中文翻譯。

| 類別 | 詞綴 | 遊戲中的語意方向 |
| --- | --- | --- |
| 重複／再做 | `re-` | 再施放、重複上一個法術 |
| 否定／反向 | `un-`、`dis-`、`in-`、`im-`、`mis-` | 解除、削弱、干擾或反制 |
| 時間／位置 | `pre-`、`mid-` | 預備護盾、調整回合節奏 |
| 數量 | `tri-` | 三連擊或三重效果 |
| 人物 | `-er` | 召喚助手或提高支援效果 |
| 特質 | `-ful`、`-less` | 增益或減益效果 |

原始欄位 `fix` 代表詞綴、`extra` 代表可合成的字根或片段，但名稱較不直觀。實作遊戲時，先轉成下列結構，不直接以欄位名稱推斷詞綴位置：

```json
{
  "id": "rerun",
  "word": "rerun",
  "affix": "re",
  "affixType": "prefix",
  "base": "run",
  "meaning": "run again",
  "translation": "再跑一次；重新執行",
  "family": "repeat",
  "difficulty": 1
}
```

後綴題標記為 `"suffix"`，由遊戲以 `base + affix` 合成；前綴題則以 `affix + base` 合成。`triplets` 的 `plets` 等少數案例是配方片段，不必宣稱它是可獨立使用的英文單字。

## 第一版遊戲循環

1. **主選單與命名**：綠旗後先顯示主選單，玩家可按「開始挑戰」或「查看排行榜」；只有按下開始按鈕才進入玩法介紹與排名名稱欄位。玩法介紹結束前隱藏全部戰鬥變數，避免畫面過載。
2. **遭遇敵人**：顯示敵人、生命值與一則英文語意提示，例如 `not happy`。
3. **煉金選擇**：玩家從詞綴符文與字根素材中，選出正確的兩個部分，例如 `un` + `happy`。
4. **合成與對戰**：作答前隱藏「煉成單字」；答對或答錯後才短暫顯示正確單字與中文翻譯。答對造成傷害並回復 1 點護盾魔力；答錯時優先消耗 1 點護盾魔力，魔力歸零後再次答錯才失去生命。
5. **樓層獎勵**：擊敗敵人後進入下一層，取得少量回復、法術強化或下一題的優勢。
6. **結算**：角色生命歸零或玩家結束挑戰時，顯示分數、抵達樓層、答對數與連擊數；將本局紀錄依「樓層優先、分數次之」更新到本機前五名。

第一版以「一題一個正確配方」為主，不必一開始加入多材料、多種資源配方或隨機裝備。RPG 的策略先由詞綴效果、生命／魔力與連擊帶出，避免英文判題被複雜系統淹沒。

## 計分與難度

| 行為 | 分數用途 |
| --- | --- |
| 答對配方 | 基礎分數 |
| 連續答對 | 連擊加成 |
| 擊敗敵人／完成樓層 | 樓層獎勵 |
| 剩餘生命或魔力 | 小幅結算加成 |
| 答錯 | 中斷連擊，但不以大量扣分懲罰 |

- 樓層是排行榜的第一排序指標；同樓層才比較分數，因此正確率與連擊仍能決定同樓層名次。
- 每題答對分數為 `100＋連擊×20`；連擊會直接提高每題得分，答錯時連擊歸零。
- 每通過一層額外取得 `200＋樓層×80` 分；樓層是排行榜的第一排序指標。
- Scratch 原型保存最多五筆不同名稱的最佳紀錄，顯示「玩家名 ＞ 樓層 ＞ 分數」；同名只有在新樓層更高，或同樓層但分數更高時才更新。
- 本機前五名在同一次開啟遊戲期間跨綠旗重玩保留，只能從主選單的「查看排行榜」進入；關閉或重新載入專案後回到空榜。永久跨裝置紀錄仍需網站排行榜 API。
- 主選單與排行榜不顯示計分公式、排序演算法或保存期限等實作資訊，只呈現玩家目標與當前名次。
- 主選單以亮金色短句提示「連擊越高，得分越多！」，讓玩家理解追求連續答對的直接價值，但不公開計分公式。
- 不把作答速度當主要分數來源，避免初學者因閱讀較慢而受挫。
- 前幾層只出現一種詞綴和少量干擾選項；之後逐步混合相近意義的詞綴、增加敵人生命與連續題數。
- 每一局使用抽題袋：在同一輪中先不重複出題，題庫用完才重新洗牌。

## 友善公開排行榜

### 名稱規則

- Scratch 本機榜必填 1–8 個英文字母或數字，以 62 格、每格 `12×16` 的 PNG 點陣字形圖集動態拼字；不載入中文字庫，控制專案與網頁負擔。
- 未來網站公開榜可另行支援經清理的中英文名稱，但不直接沿用 Scratch 的輸入限制。
- 在欄位旁明示：**請勿輸入全名、電話、Email 或其他聯絡資訊。**
- 比對名稱時，將全形／半形格式正規化、合併連續空白，並讓英文不分大小寫。因此 `Tom`、` tom ` 與 `TOM` 視為同一名稱。
- 顯示時保留玩家這次輸入、清理後的名稱；不在 Blob key 中直接放入名稱。

### 同名合併規則

排行榜以「遊戲 ID + 正規化名稱」識別一筆紀錄。

- 同名新成績抵達更高樓層時，更新該名稱的最佳紀錄。
- 同名新成績較低時，不覆蓋既有紀錄。
- 樓層相同時，只有分數更高才更新；樓層與分數都相同時保留較早的紀錄。
- 使用不同名稱時，建立另一筆排行榜紀錄；這是刻意允許的友善模式行為。

因此「同名合併」只讓排行榜更容易閱讀，並不試圖判定真實身分或防止玩家改用別名。

### 儲存資料與 API

建立一個獨立的 `word-alchemy-leaderboard` Netlify Function；不要修改或重用現有的 `play-counts` 事件儲存邏輯。

每個名稱的最佳紀錄可儲存為：

```json
{
  "version": 1,
  "gameId": "遊戲 UUID",
  "displayName": "小鹿煉金師",
  "normalizedName": "小鹿煉金師",
  "score": 2360,
  "floor": 8,
  "correctCount": 23,
  "maxCombo": 7,
  "submittedAt": "2026-09-20T00:00:00.000Z"
}
```

- Blob key 使用 `gameId` 與 `normalizedName` 的 SHA-256 雜湊值，避免名稱成為路徑或被直接列舉。
- `POST` 接收結算成績，驗證名稱、資料型別、整數範圍與請求大小，僅在新紀錄較佳時覆寫。
- `GET` 至少回傳該遊戲前 5 名與當次提交者的名次；公開讀取可快取約 60 秒，提交後的回應則立即回傳最新名次。
- 本機開發使用 `localStorage` 模擬榜單，不能讀寫正式排行榜。
- UI 使用「友善排行榜」標示，並說明名稱不是帳號、同名只保留最佳成績。

沒有帳號與伺服器逐步驗證時，玩家仍可能自行送出不合理分數。第一版只需把這件事當成友善競賽的邊界：拒絕明顯不合理的欄位值，但不為此增加登入、密碼或複雜反作弊系統。

## Scratch 與網站的串接

目前遊戲會在安全的 iframe 中執行，並維持 `sandbox="allow-scripts allow-pointer-lock"`。不加入 `allow-same-origin`。

Scratch／TurboWarp 專案本身無法自動使用網站的 Vue 狀態或安全地保存正式高分，因此遊戲結束時需透過一小段受信任的封裝橋接程式送出訊息：

```js
window.parent.postMessage({
  type: 'scratch-gallery:game-finished',
  name: '小鹿煉金師',
  score: 2360,
  floor: 8,
  correctCount: 23,
  maxCombo: 7,
}, '*')
```

外層的 `GamePlayerDialog` 只接受目前 iframe 視窗送出的這種事件，再由外層網站補上已知的 `gameId`、更新本機最佳紀錄，並以同源請求呼叫排行榜 API。沙盒 iframe 的訊息來源會是 opaque origin，不能只靠 `event.origin` 判斷；必須檢查 `event.source === iframe.contentWindow`，並嚴格驗證事件格式與數值範圍。

這個橋接只負責通知結算，不能證明分數確實由遊戲取得；它的好處是維持現有 sandbox 隔離、讓遊戲不用自行持有 API 邏輯，也不必讓 iframe 直接存取網站資料。

## 像素風格規格

### 視覺方向

- 風格：明亮、友善的 2D 像素奇幻，不走陰暗寫實或恐怖路線。
- 舞台：以 Scratch 的 480×360、4:3 畫面為主要構圖；介面採 16px 網格思考，重要角色、按鈕與資訊保持大而清楚。
- 色彩：延續網站的藍、黃、橘氣質；以深藍作地下塔背景、金黃作煉金光／獎勵、橘色作警示或敵人重點，避免只靠顏色傳達狀態。
- 質感：硬邊像素、有限色票、清楚的輪廓與小面積高光；避免平滑漸層、模糊光暈、過度細碎背景或 AI 生成的假文字。
- 字體：角色和場景可像素化，但中文題目、按鈕和名稱輸入應優先清晰易讀的系統字體；不為了像素感犧牲閱讀。

### 介面與無障礙

- 排名名稱欄位要有可見標籤、範例和欄位旁的錯誤訊息，不可只用 placeholder。
- 在網站對話框內的關閉鈕與可點控制項維持至少 44×44 px；Scratch 畫面內的主要選項也應有足夠大的點擊區域。
- 文字與背景維持足夠對比；正確／錯誤除了藍黃橘或紅綠外，也要搭配圖示、文字和動畫差異。
- 不用閃爍製造緊張感；提供關閉螢幕震動、快速特效與大音量音效的設定，並尊重 reduced-motion。
- 鍵盤玩家能以方向鍵或 Tab 選取素材，再用 Enter／空白鍵確認；焦點位置必須明顯。
- 戰鬥中的樓層、分數、連擊與敵人生命使用相同右緣靠右排列；玩家、生命與護盾魔力排列於左上，語意提示放上方中央，狀態列置於左側資訊列下方並避開 Scratch 作答輸入列。
- 四個右側戰鬥資訊框使用相同起點與寬度，左右邊緣皆成一直線；狀態列只說明答題造成的傷害、生命或護盾變化，答案與中文翻譯僅在「煉成單字」顯示一次。

### 後續產圖清單

尚未產生任何圖像。需要素材時，依序製作並在遊戲中實測可讀性：

1. 480×360 的煉金塔第一層背景。
2. 主角煉金術士的待機、施法、受傷像素精靈。
3. 3 種初期敵人的待機、受傷、消失像素精靈。
4. 前綴符文、後綴符文、字根素材與煉金鍋圖示。
5. 血量、魔力、連擊與樓層的像素 UI 元件。
6. 結算／排行榜用的卷軸或石碑背景，保留足夠空白給可讀文字。

產圖提示需固定包含：`2D pixel art`、`crisp hard edges`、`limited palette`、`child-friendly fantasy`、`no text`、`no watermark`。需要透明背景的角色、敵人、道具須明確要求透明背景；產出後以最近鄰縮放檢查，不使用模糊插值。

## 實作順序

1. 確認正式遊戲名稱、角色主題與第一版的敵人設定。
2. 將 `girrafe.json` 整理成遊戲題庫格式，補上詞綴位置、家族與難度。
3. 先完成沒有排行榜的 Scratch 可玩原型：命名、答題、戰鬥、爬塔、結算。
4. 在 TurboWarp 打包流程加入結算 `postMessage` 橋接，並在本機確認 iframe 能正確傳遞資料。
5. 新增排行榜 Function、Blob schema、前端接收與本機模擬；為名稱合併、排序、輸入驗證與訊息驗證寫測試。
6. 製作像素背景、角色與敵人素材，接著調整難度與分數。
7. 匯入作品、選擇封面、執行 `npm run verify`；涉及遊戲播放器與安全政策時再執行 `npm run verify:local`。

## 尚待確認

- 遊戲正式名稱、主角是人類煉金術士或長頸鹿角色。
- 每層是一個敵人或一組連續敵人，以及首局預期時長。
- 詞綴法術效果是否完全依家族固定，或讓玩家在局內選擇升級。
- 第一版排行榜顯示在結算畫面、作品介紹頁，或兩者都有。
- 100 題完成後是否要繼續增加新的詞綴家族與難度級別。
